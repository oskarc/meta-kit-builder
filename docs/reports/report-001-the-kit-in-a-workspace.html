The Kit in a Workspace

The kit had no statement about workspaces to contradict. Its hooks were written for one project, and read that way they are right. Where they go wrong is when a session holds two.

verified — what Claude Code does

Where each thing loads from

verified

Hooks come from one directory: the one the session started in.

Hooks and every other .claude/settings.json key load from the current working directory's .claude/ folder, with no parent-directory fallback, plus user and managed settings. A directory added with --add-dir contributes only enabledPlugins and extraKnownMarketplaces from its settings. A directory listed in permissions.additionalDirectories contributes nothing.

Permissions reference, "Additional directories grant file access, not configuration"; Settings reference, "Where Claude Code keeps the local file".

verified

${CLAUDE_PROJECT_DIR} is the launch directory and never moves.

It points at the project root where the session started. After Claude enters a worktree, or after /cd moves the session to another directory, it still points there. The hook's cwd input field is what follows Claude.

Hooks reference, "Reference scripts by path"; Permissions reference, "Move the session to another directory".

verified

/cd swaps the project configuration, hooks included.

On a move the new directory's settings, hooks, skills and subagents apply and the previous directory's project MCP servers disconnect. Requires v2.1.246 or later.

Permissions reference, "Move the session to another directory".

verified

An added directory gives its skills and agents, not its rules.

From a directory passed with --add-dir or /add-dir: skills load with live reload, commands and subagents load without it, CLAUDE.md and .claude/rules/ load only when CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 is set. Adding the .claude folder itself, rather than the repository root, adds nothing, because the loaders look for <dir>/.claude/.

Permissions reference, the table under "Additional directories grant file access, not configuration"; Skills, "Load skills from a directory outside the project"; Memory, "Load from additional directories". The last sentence is this session's own case: two forks' .claude subfolders were added and none of their agents appeared.

verified

Subagents are found walking up from the working directory, and from added directories.

Every .claude/agents/ between the working directory and the repository root is scanned; the definition closest to the working directory wins a name. Added directories' agents load too. A project subagent's frontmatter hooks run only once the folder holding the agent file is trusted, and an added directory outside the trusted repository needs its own trust.

Subagents reference, "Choose the subagent scope" and "Hooks in subagent frontmatter".

verified

Settings hooks fire inside subagents, carrying agent_id and agent_type.

Hooks reference, "Hook locations"; Subagents reference, "Define hooks for subagents".

verified

Plugin subagents lose their frontmatter hooks.

For security reasons a plugin's agents ignore hooks, mcpServers and permissionMode. The kit's agents carry their blinds and write scopes in exactly those hooks.

Subagents reference, the note under "Choose the subagent scope".

verified

Nested configuration below the launch directory loads on touch, except settings.

A subdirectory's CLAUDE.md and .claude/skills/ load the first time Claude reads a file there. A subdirectory's .claude/settings.json never loads: project settings are not inherited in either direction.

Memory, "How CLAUDE.md files load"; Skills, "Load skills in monorepos and subdirectories"; Large codebases, "Choose where to start Claude".

verified

Three events tell a hook where Claude is.

DirectoryAdded carries the absolute path of a directory added mid-session; CwdChanged carries cwd and previous_cwd; every tool event carries cwd and the tool's own file_path. No event reports the directories added at launch with --add-dir.

Hooks reference, event sections for DirectoryAdded, CwdChanged, SessionStart; "Common input fields".

verified

The kit's hooks anchor everything on CLAUDE_PROJECT_DIR.

lib.sh sets ROOT from CLAUDE_PROJECT_DIR, falling back to the shell's directory, and every record path derives from it. The settings template and all eight agent files reference their scripts as ${CLAUDE_PROJECT_DIR}/.claude/skills/meta-mechanisms/hooks/…. The write scopes are bare path fragments such as meta-ledger/LEDGER.yaml.

Read in full: meta-mechanisms/hooks/lib.sh, templates/settings.template.json, agents/*.md frontmatter.

verified

Two hooks act on any path that contains /.claude/skills/, whichever repository it belongs to.

post-read.sh and owner-check.sh match the tool's file path by that fragment alone and write into the primary kit's telemetry. On a fixture of two installed kits with the hooks anchored on kit A, a Read of kit B's meta-map/SKILL.md wrote loaded|meta-map/SKILL.md into kit A's telemetry. Kit A then counts that skill as loaded this session.

Fixture run 2026-09-17 in this session; the two scripts read in full.

verified

The kit's own tree runs no mechanisms in a session started there.

Its manifest declares kit_type: base, which every hook treats as "not installed", and it ships no .claude/settings.json. A workspace session started in the base kit therefore governs nothing, whatever it adds.

lib.sh kit_installed; this repository's .claude/ holds only a local permissions file.

A session holding two kits

judgement — what follows

Three consequences

verified

Only the primary kit's lifecycle runs, and it mis-logs the other.

Edits to kit B's records are ungoverned: no backlog, no stop-gate task, no ownership check for B. And A's telemetry gains loads and bypasses that happened in B, so A's map evidence and ownership evidence are wrong in both directions. Reproduced on the fixture above.

derived

After /cd, the kit's hooks point at the wrong tree or at nothing.

The moved-to directory's settings register its hooks, but their command paths expand ${CLAUDE_PROJECT_DIR} to the launch directory. From a non-kit start the scripts do not exist there, so every event reports a non-blocking failure and the kit is silently off. From another kit's start the scripts run, but with ROOT still the first kit, so they read the first kit's records. Derived from two verified claims; not executed.

derived

Two copies of every kit agent and skill, and the scopes cannot tell the repositories apart.

Both kits' .claude/agents/ and .claude/skills/ load, so the eight kit agents and eighteen meta skills appear twice by name. Which copy answers to a name is not documented for the added-directory case. Whichever runs, its write scope is a bare fragment, so an agent asked to record observations for A may write B's ledger without any hook objecting.

recommendation · judgement

Do A now, draw B as the next contract

The plain answer to "how do the hooks work in a workspace" is: they don't, not for the second kit. Claude Code registers hooks from one directory only, the one the session started in, and reads every other directory for files, skills and agents. So a workspace is one governing kit per session, and the other repositories are files. That is workable today if it is said, and if the kit stops mis-logging the other repositories' reads and edits into its own evidence, which is one rule in the library.

To govern two kits from one session, the kit has to become root-aware. Claude Code gives enough to do it: every tool event carries the file's path, cwd follows Claude, DirectoryAdded names what was added, and a script can walk up from any path to the nearest installed manifest. That is option B, and A is its first guardrail. Neither C nor D is worth building: C puts the records outside the repositories, D drops the agents' blinds.

Until B ships, the rule of thumb for the pioneer: start the session in the repository whose kit should run, add the others by their root path with --add-dir, expect their skills and agents and not their hooks, and do not edit their records from that session.
