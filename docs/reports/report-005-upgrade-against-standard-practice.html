The kit's upgrade, held against how software is upgraded

Installing and upgrading the kit is a software upgrade, and that problem is solved. The procedure was read in full against the standard practice, each practice taken from its own documentation. It already does five of the twelve things. It lacks four outright, and three of those would have prevented what the rehearsals found.

Sources first, then the text, then one test

verified — one test

The merge the kit needs already exists

The rehearsal's own case was given to git merge-file: the skill as the old kit shipped it, the project's copy with its two added lines, and the new kit's skill. It works on plain files; the project need not be a repository.

result

The project's two lines, put back on the new skill, in one command.

Exit code 0, and the output is character for character what the rehearsing agent produced by hand: the new kit's skill with the project's lines at the end.

result

An edit inside a kit sentence keeps its place.

The project changed two words in a line the new kit left alone. The merge kept the project's wording exactly where it was. The kit's own script reports that whole line as "the project's", with no place to put it back; an agent would have to guess.

result

A real conflict is reported by the tool, not judged by the agent.

The project edited a line the new kit also rewrote. Exit code 1 — the count of conflicts — and both versions are set side by side between markers, labelled project and new-kit. That is exactly what the sheet needs beneath a skill's line: "a residue line that cannot be reapplied cleanly" stops being a judgement.

The same merge fits the record headers that went wrong in the third rehearsal: base, the old template's header; current, the record's header with the pioneer's notes; other, the new template's. It does not help a project installed before the kit kept installed copies, which has no base; the line history stays as the fallback there.

judgement — what is underneath

Two causes behind most of the procedure's length

cause

The program and the project's data share folders.

A kit skill, which an upgrade should replace wholesale, sits in the same folder as the record the project owns: the ledger skill beside the ledger. That one fact is why a kit can never be folder-copied, why staging has to strip out the kit's own records, why the staged manifest is a contradiction, why there is a template rule at all, and why this repository ships records that every install must replace. Software that keeps what it ships apart from what the user writes upgrades by replacing a folder. This is a change of shape, and itself a migration; it is named here, not proposed yet.

cause

The procedure is performed twice by hand, once to test and once for real.

Standard practice builds the new state beside the old, verifies it, and swaps. The kit already builds and verifies it — and then throws it away. Promoting the rehearsed copy, after the pioneer's answers are applied to it, would make the tested result the installed one, give a rollback for free (the old folder is still there), and remove the question of what happens when a run dies half way.

verified — what is the kit's own

Two things with no off-the-shelf answer

The one who carries out the procedure is an agent reading prose, and what the pioneer has written into a skill is judgement in natural language. So: how a runbook is written for an agent to follow, and how a conflict is put to someone who decides by meaning rather than by diff. Google's book ranks automation from "No automation" up to "The database ships with its own failover script"; the kit sits between, shipping some of its own scripts and performing the rest from a document. Every rehearsal has moved one more step from the document into a script, which is the ordinary direction.

recommendation · judgement

Draw the contract in these terms

Not a list of the rehearsals' gaps, but the four missing practices, which cover the gaps that mattered:

  • Snapshot, order, rollback. The run starts from a clean commit or a kept copy. The comparison bases — old templates, installed copies — are replaced last, not first. The procedure says how to go back, and that a failed run is restored and started again rather than continued.
  • Preconditions. Clean tree, whole staged kit, no open review batch, no other session; checked by a script before anything is read.
  • A built release. One command produces the staged kit, with a list of its files and their checksums, and step 1 verifies the staged folder against that list. The kit's test builder uses it.
  • The merge. git merge-file does the reapplying and finds the conflicts, for skills and for record headers. This needs a ruling from the pioneer: the kit's own rule limits its scripts to bash, sed, awk, grep, tr and date. Allow git: the merge becomes mechanical and the kit's own residue script shrinks to the fallback for old installs; git must then be present wherever the kit is upgraded, which Claude Code already requires on Windows and which a project under version control has anyway. Keep the rule: reapplying stays the agent's judgement, as now, with the risks the test shows.
  • Tests that do not write into live records. The hook test runs against a scratch copy, which also repairs the hold on the first review batch; the travelling walk is run by the procedure from its own fixture, or no longer shipped.
  • From the rehearsals, only what these do not already cover: a default for every standing question, counts on the sheet from named commands.

Left for later, each as its own decision: promoting the rehearsed copy instead of repeating the run; migrations chosen by version; keeping the program apart from the project's data.
