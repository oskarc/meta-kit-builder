Two Stops and a Done

Where the install and the upgrade stop for the pioneer, why each stop is where it is, and how both flows become one sheet of questions, a silent run, and an ending that says so.

what the pioneer said

The complaint, taken as the spec

"it can feel neverending and lacks a clear 'NOW ITS DONE, and you are good to go.' its more of a 'I suppose i can start working..?'"

Two defects, not one. The first is the number and placement of stops: each question is asked where the step reaches it, so the pioneer is pulled back six or seven times across a flow whose questions were all knowable near the start. The second is the ending: the install closes with a question ("What would you like to build first?"), the upgrade closes with "accept the report", and the next turn's stop-gate hands over a kit task. Nothing says done, and the first thing after the last stop is another ask.

the mechanism, drawn

Where the pioneer is pulled in, today and proposed

judgement — the design

One sheet, a silent run, and a done block

design

The sheet: every question at once, prefilled with the default the rehearsal used.

For an upgrade the rehearsal already knows the whole list. The sheet is that list, one line per question, each carrying the default the stub used and the consequence of the default in a few words. The pioneer answers with one word, "defaults", or changes lines. Conflicts a reapply would hit are lines on the sheet with the two resolutions, so the real run never asks. The tree-or-commit question and the acceptance of the report join the sheet: "measure residue from the tree", "remove the staged kit when the report is written". One stop.

For an install the sheet comes after Step 2's reading, because everything on it is known then: is this orientation right; the applications; integrate the library kit found or not; the CLAUDE.md block and the settings merge shown as the plan they are, not as two permissions; ratify the map now or later. The founding statement keeps its own moment, after the sheet, because the kit says it is "not a form to fill in" and the aspect that makes it the pioneer's would be cheapened by a checkbox beside it. Two stops.

design

The run: no stop after the sheet, by construction.

Steps 5 to 7 of the install and 3 to 9 of the upgrade run on the sheet's answers. The rehearsal's pass rule already forbids a question that is not on the list; the sheet makes the list the contract for the real run. A question the real run meets that the sheet did not carry is a defect to record, exactly as a troubleshooting step is today, never a stop.

design

The ending: a done block with the same shape every time.

Installed, or upgraded to version X. What was verified, as counts: checks passed, hooks that fired, the baseline written. What is not waiting on you, said plainly when nothing is. What is waiting and when it will ask: the map entries if the pass was deferred, drift entries at mitigated if batches were chosen, each with the one word that summons it. Then the sentence the pioneer asked for, in those terms: done, start working. The stop-gate stays as it is; the block tells the pioneer what it will say next, so the first backlog line reads as a list, not as the next task.

verified

What the sheet does not reduce: decisions.

A sheet of nine lines is nine decisions. The pioneer's failure condition counts decisions, and the count is set by the project's state, not by when the questions are asked. The sheet changes the number of times the pioneer is pulled back and the sense of an ending; it does not change what has to be decided. Defaults make the common answer one word.

What this pass could not close

  • open Whether the stub answers are the right defaults for the sheet. They were chosen to exercise the code in rehearsal (reapply hits conflicts, legacy edits the file), not as what a pioneer usually wants. The baseline of C-013 says replace; the first two real runs said batches, overwrite, none for now.
  • open How long a sheet gets on an old fork. The 0.15 run had twelve differing skills; a sheet of twelve reapply lines plus eight standing questions is twenty lines. Whether that reads as one stop or as a wall is the pioneer's judgement.
  • open Whether the first session after an upgrade should hand over a batch at all when the upgrade itself created the backlog. The gate is right by its rule; the feeling is the pioneer's evidence against the rule, and only a rule change or a grace marker answers it.
  • open The install has never been run end to end by this kit on a fresh project since v0.14; the stop count is from the text, not from a run.
recommendation · judgement

Option A, as contract-011

The sheet and the done block are procedure text and two walk states, the same shape as contracts 009 and 010. The upgrade's version is the stronger case, because the rehearsal already computes the sheet and today throws it away. The install's version keeps the statement's own moment. The gate's behaviour after an upgrade is the one question worth putting to the pioneer before drawing: leave it, or let the done block's "nothing is required now" be true for the rest of that session.
