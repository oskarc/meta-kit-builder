- **T-4 (the pre-mortem: the rehearsal on a copy of a real install).** The Classes copy was rehearsed three times. The final round's numbers, 17 / 14 / 2, meet the first condition (every decision belongs to a differing file or a standing question) and miss the second by two steps that were the agent's own scripting, not the procedure. Two things this round established that no earlier one did:

- **The carriage-return fallback is load-bearing, not a nicety.** The fixture's baseline is pre-0.15 and hashes

It also recorded a third instance of the pattern `drift-003` names: `meta-map/SKILL.md` states a byte figure for

## Round 5 on the Classes copy — a fail, and what it taught

**21 decisions / 13 files genuinely differed / 3 troubleshooting — FAIL.** Every decision was admissible: 13 for
the kit files that differ, 5 header questions the template rule forced, 3 standing questions. The failure is the
third number, and all three sat in step 7 — in clauses added between Classes round 4 and round 5 to fix earlier
rounds. That is the lesson of this round: each fix added text, and the added text had its own holes.

- "each field at the position the staged template gives it" named an anchor that none of the project's 80
  contract entries has, so the agent had to invent one.
- No method was given for a migration of 1,068 field insertions across three records, only "by hand".
- The rule said how to append the pending marker to a `note:` that exists, and nothing about the 91 nodes with
  none.

**The repair was to make step 7 shorter, not longer.** Field order now carries no meaning and no anchor is
named; the tooling is the agent's choice and the *verification* is the requirement — diff the migrated file
against a copy taken before the migration and confirm every pre-existing line survives; and the `note:` rule
covers both cases in one clause. The header-refresh rule, which the agent named as the biggest ambiguity and
which swung the headline number from 16 to 21, is now decided file by file rather than project by project.

Three findings from this round are for the pioneer rather than the procedure:

- **Keeping an old template has a bill that recurs.** The kept manifest template has no `base_kit_version`,
  `kind`, `load`, `triggers` or `owns`, so at every future upgrade each base node line reads as pioneer-changed
  and can never be refreshed mechanically. The procedure now says this at the moment of asking.
- **Answering *keep* to all thirteen leaves a working install whose own documentation describes a different
  kit.** Not one kept file mentions the ledger, casebook, correction log, map or mechanisms, and the map entry
  for upgrades points at a kept bootstrap that has no upgrade section.
- **A marker key the hooks read can be silently absent.** Fifteen of the fork's 54 drift entries carry no
  `status:` at all, so the backlog miscounts and nothing in the upgrade noticed. The migration list now
  backfills it.

Report: `upgrade-rehearsals-2026-09-13/classes-round5.md`.

## Round 10 on fx013 — the simplified step 7 confirmed, and one sentence that cannot be satisfied

**3 decisions / 1 file genuinely differed / 0 troubleshooting — PASS.** First run on the text after step 7 was
made shorter. The agent was asked for a verdict on five specific points and gave one on each.

- **Dropping the named anchor for new fields was right.** The case it anticipated was live: the fixture's
  contract has no `tier_4`, so an instruction to insert after that field would have pointed at a line that does
  not exist and forced exactly the improvisation the sentence was meant to prevent.
- **The verification requirement has a real flaw and it is the one defect worth acting on.** As literally worded
  the check cannot pass. The same step mandates refreshing header comment blocks and removing three retired score
  keys, and both change pre-existing lines. The sentence needs to say every pre-existing *record* line.
- **The pending-entry note clause is unambiguous on the page and was never exercised**, because this fixture has
  no project nodes. The wording is vouched for; its execution is not.
- **The ordering fix holds, and the trap it closes is silent.** Step 5 overwrote all ten templates, six of them
  materially, so deferring the comparison would have compared a staged template against itself and raised no
  error at all. One residue: the instruction to write the comparison down never says where.
- **The line-ending fallback, measured again on this fixture:** 49 of 70 baseline entries matched only through
  it, and without it the run asks 34 decisions instead of 3.

It also notes, correctly, that on the real 0.14 to 0.15 hop nothing inside the project routes the agent to the
staged bootstrap, because the staged-kit backlog line exists only in the newer hook. That is `gap-032` and the
pioneer's staging sentence carries it.

The agent disclosed one slip of its own, a script that invoked the walk twice and pushed the shell call into the
background, and did not count it. It says plainly that if the pioneer counts it the third number is 1 and the
run fails. Recorded as it was reported.

Report: `upgrade-rehearsals-2026-09-13/fx013-round10.md`.
